API domains

The public API surface is organized around the booking journey:

  • events and event sessions, including search and detail views;
  • venues and seats for browsing availability;
  • reservations, including temporary holds and pricing preview;
  • payments, including test-mode confirmation and webhooks handled server-side;
  • tickets, including issuance and validation states;
  • user and profile data for signed-in customers;
  • refunds for eligible confirmed reservations, as explained in the refund and cancellation policy;
  • assistant features only where the AI assistant is enabled.

Representative relative paths used by the web client include:

GET /api/events?size=1
GET /api/venues?size=1

Paths are shown without any host or port on purpose: the browser calls the deployed gateway for the current origin, never a hardcoded internal address.

Authentication

The API uses token-based sign-in managed through the configured authentication provider. Browsers attach the session token to API calls automatically; guests use scoped checkout proof for their own reservation only. All role and ownership checks run on the server. Never share tokens, and never place credentials, ticket codes, or payment secrets in documentation examples. How sessions and roles work at a high level is summarized on the security page.

Server-authoritative invariants

  • Each reservation is limited to 10 seats.
  • Seat holds expire after 15 minutes against the server clock.
  • Seat ownership is decided by the database; browser state is reconciled against it.
  • Role checks for customer, staff, and admin surfaces run on the server.
  • Refund eligibility is decided by the server under the refund and cancellation policy.

Client behavior, including the AI assistant where enabled, cannot bypass these rules. See the Terms and Conditions for the product wording.

Live documentation

No live interactive documentation endpoint is linked from this deployment. Internal addresses, internal ports, and per-service documentation consoles are intentionally not exposed here because they are not part of the public portfolio surface. Authors and reviewers should consult the version-controlled backend service contracts in the repository instead of expecting a public console.

Protected surfaces

Admin, staff, scanner, operational, and internal endpoints remain protected by authentication and role checks. This page gives no guidance for getting around those checks and lists no administrative or operational internals. For questions about using the public site, see the frequently asked questions or the contact page.

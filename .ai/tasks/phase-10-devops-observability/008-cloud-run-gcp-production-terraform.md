## 2. Objective & Invariants

Use Terraform to provision isolated staging/production foundations for Cloud Run, regional HA Cloud SQL PostgreSQL 16, Memorystore Redis, Secret Manager access, Cloud Armor and external HTTPS load balancing. The code supplies infrastructure and identity only; CD supplies immutable application revisions and secret values at runtime.

### Critical Invariants to Enforce:
- [ ] Production Cloud SQL is regional HA with automated backups and point-in-time recovery; each microservice has a least-privileged database/user and migrations remain forward-only/backwards compatible.
- [ ] Cloud Run never stores secret values in Terraform state, image layers, YAML, environment files, command history, or outputs; it references Secret Manager versions at runtime.
- [ ] Cloud Run services use private egress/VPC connectivity for Cloud SQL and Memorystore; public ingress is limited to the HTTPS load balancer/Gateway design.
- [ ] Redis/Memorystore is never a reservation lock/source of truth; PostgreSQL constraints/transactions and the Kafka transactional outbox remain unchanged.
- [ ] Cloud Armor protects public edge traffic, while service authentication/authorization remains enforced by Gateway and backend JWT validation.
- [ ] Terraform destroys nothing by default in production; `prevent_destroy` protects database, Redis, secrets and Terraform state-critical resources.

## 4. Technical Specifications & Contracts

### 4.1 Terraform and State Contract

```hcl
terraform {
  required_version = ">= 1.9.0, < 2.0.0"
  required_providers {
    google = { source = "hashicorp/google", version = "~> 6.0" }
    google-beta = { source = "hashicorp/google-beta", version = "~> 6.0" }
  }
  backend "gcs" {}
}

provider "google" { project = var.project_id; region = var.region }
```

Each environment backend is supplied locally/CI via a non-committed `backend.hcl`, for example `bucket = "seatflow-tf-state-production"` and `prefix = "runtime"`. The bootstrap project enables state bucket versioning, uniform bucket-level access, retention policy, and CMEK as a separately approved platform bootstrap prerequisite. Never use a local backend for staging/production.

### 4.2 Network, Data and Secret Contract

```hcl
resource "google_sql_database_instance" "postgres" {
  name             = "seatflow-${var.environment}-postgres"
  database_version = "POSTGRES_16"
  region           = var.region
  settings {
    tier              = var.environment == "production" ? "db-custom-2-7680" : "db-custom-1-3840"
    availability_type = var.environment == "production" ? "REGIONAL" : "ZONAL"
    backup_configuration { enabled = true; point_in_time_recovery_enabled = true; transaction_log_retention_days = 7 }
    ip_configuration { ipv4_enabled = false; private_network = google_compute_network.seatflow.id }
  }
  deletion_protection = var.environment == "production"
  lifecycle { prevent_destroy = true }
}

resource "google_redis_instance" "runtime" {
  name           = "seatflow-${var.environment}-redis"
  tier           = var.environment == "production" ? "STANDARD_HA" : "BASIC"
  memory_size_gb = 1
  redis_version  = "REDIS_7_0"
  authorized_network = google_compute_network.seatflow.id
  lifecycle { prevent_destroy = true }
}
```

Create separate application databases/users named `seatflow_user`, `seatflow_seatmap`, `seatflow_event`, `seatflow_reservation`, `seatflow_payment`, `seatflow_ticket`, and `seatflow_notification`; `realtime-service` has no own relational DB unless its current module requires one. Generate database passwords outside Terraform state, add them as Secret Manager versions through the approved secure procedure, and grant only each service account `roles/secretmanager.secretAccessor` on its own allowed secrets.

Create secret *containers* for each required runtime key: `db-<service>-password`, `kafka-bootstrap-servers`, `redis-host`, `redis-password`, `jwt-jwk-set-uri`, `jwt-issuer-uri`, `stripe-api-key`, `stripe-webhook-secret`, `otel-exporter-otlp-endpoint`, and CORS/public-origin configuration. Service-specific maps must ensure payment alone accesses Stripe write credentials; Gateway/backend services receive only the JWT/public values they need.

### 4.3 Cloud Run Contract

Define 10 services: `api-gateway`, `eureka-server`, `user-service`, `seat-map-service`, `event-service`, `reservation-service`, `payment-service`, `ticket-service`, `realtime-service`, and `notification-service`; plus one `seatflow-<environment>-migrations` Cloud Run Job. Use image digest/placeholder image only to create an initial service; P10-007 updates it to an immutable Artifact Registry image.

```hcl
resource "google_cloud_run_v2_service" "service" {
  for_each = local.services
  name     = "seatflow-${var.environment}-${each.key}"
  location = var.region
  template {
    service_account = google_service_account.runtime[each.key].email
    scaling { min_instance_count = each.value.min_instances; max_instance_count = each.value.max_instances }
    containers {
      image = var.bootstrap_image
      ports { container_port = each.value.port }
      env { name = "SPRING_PROFILES_ACTIVE"; value = "prod" }
      env { name = "SEATFLOW_DEPLOYMENT_ENV"; value = var.environment }
      env { name = "DB_PASSWORD"; value_source { secret_key_ref { secret = google_secret_manager_secret.db_password[each.key].secret_id; version = "latest" } } }
    }
    vpc_access { connector = google_vpc_access_connector.serverless.id; egress = "PRIVATE_RANGES_ONLY" }
  }
  lifecycle { ignore_changes = [template[0].containers[0].image]; prevent_destroy = var.environment == "production" }
}
```

Gateway receives external traffic through the load balancer. Business services use internal-only ingress (`INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER`) and IAM invoker binding only for Gateway/approved platform service accounts. Use service minimum/maximum values: Gateway 2/20 production, reservation/payment/ticket 2/20, other JVM services 1/10; staging minimum 0 unless a realtime smoke/SLO requirement needs one. Configure 512Mi–1Gi memory and concurrency 40 for stateless APIs, then record service-specific decisions in `local.services`.

### 4.4 HTTPS Edge and Cloud Armor Contract

`edge.tf` creates a global static IP, serverless NEG to Gateway, HTTPS backend service, URL map, managed certificate, target HTTPS proxy, forwarding rule, and Cloud Armor policy. Cloud Armor rule priorities are exact: `1000` deny IPs in `var.blocked_cidrs` (403); `2000` throttle 120 requests/minute per IP to `/api/reservations` and `/api/payments` (429); `2147483647` allow. Gateway RedisRateLimiter remains an application-level second layer keyed by user/IP. Do not treat Cloud Armor throttling as authorization.

### 4.5 Verification and Runbook Contract

The runbook must include: prerequisite APIs/quotas, backend bootstrap, `terraform init/validate/plan/apply` commands, two-person production plan approval, DNS/certificate validation, Secret Manager version injection procedure, Cloud SQL backup/PITR test, Cloud Run revision rollback, WIF principal/service-account bindings, and an explicit prohibition on `terraform destroy` in production.

`verify-gcp-foundation.sh <staging|production>` asserts enabled APIs, regional Cloud SQL status, correct HA setting in production, Redis status/network, all ten Cloud Run services/job, Gateway NEG/backend/HTTPS certificate/Armor attachment, service account/secret IAM bindings, and that no Terraform output contains a secret value.

## 5. Step-by-Step Implementation Sequence (For Builder / Implementer)
1. Checkout `feat/p10-008-cloud-run-gcp-production-terraform`; read ADR-007 and obtain approved GCP project/region/DNS names and remote-state bootstrap details from platform owners before apply.
2. Write/pin provider/state configuration, build reusable module inputs/outputs, and create separate staging/production roots with no secret values.
3. Provision VPC/private-service networking, VPC connector, HA SQL, service databases/users, Memorystore and Secret Manager containers/IAM.
4. Create per-service Cloud Run accounts, services and migration job; use least privilege, private ingress for internals, runtime secret refs, production deletion protection, and image-change ignore rules.
5. Build external Gateway HTTPS path with serverless NEG, certificate/DNS dependencies and specified Cloud Armor throttling/block rules.
6. Run Terraform format/validate and a reviewed plan in staging; apply staging, add secrets securely, deploy test revision via P10-007 scripts, and execute verification runbook.
7. Repeat with a separately approved production plan only after staging verification succeeds; commit no state, tfvars, backend config, credentials, or secret output.
